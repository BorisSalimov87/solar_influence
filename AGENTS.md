# AGENTS.md — проект с графом знаний

## 0. Цель и образ результата

Проект исследует связь полного электронного содержания (GEC) ионосферы с площадью
областей, похожих на корональные дыры Солнца. Корень проекта — хранилище Obsidian:
каждый файл проекта — узел графа, ссылки `[[…]]` — рёбра. Пользователь ставит задачи
словами в сессии. Твоя работа:

1. записать задачу пользователя заметкой в `tasks/` и разделить её на подзадачи, если необходимо;
2. выполнять подзадачи по очереди, вести их статусы и по каждой сообщать итог;
3. по ходу работы достраивать граф проекта по онтологии `ontology.yaml`.

Новая сессия начинается с чтения `tasks/`, `STATUS.md` и `diary.md`: по статусам
видно, что сделано, что в работе и что ждёт решения человека.

После каждого сообщения пользователя в проекте существуют:
- заметки задач и подзадач с актуальными статусами и итогами;
- результаты выполненных подзадач — то, что требует их «Готово, когда»;
- заметки обо всех объектах работы в `notes/`, связанные между собой и с файлами;
- заметки классов онтологии в `ontology/`; настройки хранилища в `.obsidian/`.

## 1. Критерий готовности

У каждой задачи статус «выполнена» или «заблокирована»; у выполненной задачи есть
раздел «Итог». Для данных проекта: `data/gec-0km-2025-hours.csv` построен командой
`.venv/bin/python src/build_specific_gec.py`, а `.venv/bin/python checks/check.py`
на текущем источнике ожидаемо даёт `FAIL: 2 hole times missing in GEC` (нет
2025-11-26). Это известное ограничение, а не гейт шага.

## 2. Граф проекта

### 2.1. Хранилище

Хранилище — корень проекта, а не отдельная папка. В `.obsidian/` создай два файла.
Если файл уже есть (его создаёт Obsidian при первом открытии папки), допиши в него
недостающие ключи, остальное не трогай.

`.obsidian/app.json` — Obsidian показывает все файлы проекта, включая данные и код:

```json
{"showUnsupportedFiles": true}
```

`.obsidian/graph.json` — вид «Граф» показывает файлы и раскрашивает узлы:

```json
{"showAttachments": true, "showOrphans": true, "showArrow": true,
 "colorGroups": [
  {"query": "path:ontology", "color": {"a": 1, "rgb": 9474192}},
  {"query": "[status:открыта OR \"в работе\" OR заблокирована]", "color": {"a": 1, "rgb": 14254635}},
  {"query": "path:tasks", "color": {"a": 1, "rgb": 16761685}},
  {"query": "[type:Расчет OR Скачивание]", "color": {"a": 1, "rgb": 1153422}},
  {"query": "path:notes", "color": {"a": 1, "rgb": 5987296}}
 ]}
```

### 2.2. Онтология в графе

`ontology.yaml` — схема: классы, отношения, правила. Прочитай её первой. Для каждого
класса из `ontology.yaml` должна существовать заметка `ontology/<Класс>.md`:

```
---
kind: класс
---
# <Класс>

<определение из ontology.yaml>

Отношения от этого класса: <отношения, у которых класс в domain>.
Атрибуты: <атрибуты, у которых класс в domain, с допустимыми значениями>.

## Связи
- подклассОт: [[<надкласс>]]
```

Если отношений или атрибутов у класса нет, пиши `нет`. У верхних классов
(`parent: null`) раздел «Связи» пустой. Если заметок классов нет или `ontology.yaml`
изменился — создай или обнови их; удобно сделать это одним скриптом на Python,
который читает `ontology.yaml`.

### 2.3. Заметки об объектах

Каждый объект работы — заметка `notes/<название>.md`:

```
---
type: <Класс>
---
# <название>

<2–4 строки: что это, откуда взято, числа с единицами>

## Связи
- тип: [[<Класс>]]
- <отношение>: [[<название другой заметки>]]
```

Правила:
- Название называет экземпляр: «Данные GEC 2025», «Расчёт среднего GEC по исходному
  ряду». Не использовать названия классов для названия заметок.
- В названии нет символов `/ \ : # | [ ]`: символ `/` создаёт вложенную папку, и
  ссылки на заметку ломаются.
- Строка `- тип: [[<Класс>]]` обязательна: она связывает объект с его классом в графе.
- Остальные связи — только отношения из `ontology.yaml`, от области определения к
  области значений. Связь записывается в заметке, от которой она идёт.
- Файлы проекта — данные, код, проверки — отдельных заметок не получают: на них
  ссылаются по пути от корня в тексте заметки, например
  `[[data/gec-0km-2025.csv]]`, `[[src/calc_gec_average.py]]`. В `ontology.yaml` нет
  отношения к `Файл`, поэтому путь в тексте — единственная связь с файлом.
- Набор данных — заметка `notes/<название>.md` с типом `Данные`; CSV-файл
  указывается ссылкой в её тексте. Заметки `Данные` нужны для правил П1 и П2.
- Расчет — заметка `notes/<название>.md` с типом `Расчет`; связи `использует`
  (к `Данные`) и `закрывает` (к `Задача`) обязательны. Поле `status` в заметках
  расчётов не пишется: статусы живут в `tasks/`.
- Названия заметок во всём проекте различны: задача «Посчитать средний GEC…»,
  расчёт «Расчёт среднего GEC…».
- Заметку создавай в момент, когда объект появился в работе: набор данных — при
  чтении, расчёт — после запуска.
- Объект, для которого в онтологии нет класса, — новый тип и строка «Новый тип:
  <почему>». `ontology.yaml` не меняй: решение о новом классе принимает человек.
- Ссылки `[[…]]` в тексте заметок не берутся в обратные кавычки: внутри кода
  Obsidian их не показывает.

### 2.4. Задачи

Сообщение пользователя, которое требует работы с файлами проекта, — новая задача
верхнего уровня, даже если она продолжает прежнюю. Вопрос, на который достаточно
ответить словами, задачей не становится.

Заметка задачи — `tasks/<название>.md`, название — действие. Запрос пользователя
сохраняется дословно, только у задачи верхнего уровня.

```
---
type: Задача
status: открыта
---
# <название>

Запрос пользователя: «<его слова дословно>»

Готово, когда: <проверяемое условие: файл, число, команда и её результат>
Не входит: <что делать не нужно>

## План
- <название подзадачи>
- <название подзадачи>

## Связи
- тип: [[Задача]]
- подзадачаОт: [[<родительская задача>]]
```

Подзадачи:
- Если необходимо, раздели задачу на 2–5 подзадач: каждая заканчивается объектом,
  который её закрывает (расчёт, проверка, отчёт). Порядок выполнения — раздел «План»
  в заметке родительской задачи: названия подзадач по строке, без ссылок.
- Запиши задачу и все подзадачи со статусом «открыта» до любых расчётов и покажи
  план пользователю: по строке на подзадачу. Чисел, которых ещё нет, в заметках
  задач не пиши.
- У подзадачи — связь `подзадачаОт` к родительской задаче; у верхней задачи этой
  строки нет.

Статусы (поле `status`):

| статус | кто ставит | когда |
|---|---|---|
| открыта | агент | задача записана |
| в работе | агент | начал выполнять |
| выполнена | агент | условие «Готово, когда» проверено командой; раздел «Итог» записан |
| заблокирована | агент | условие недостижимо: причина и вопрос пользователю в разделе «Итог» |
| принята | агент | существует подтверждение выполнения словами пользователя |

- Статус меняется в момент события, по одной подзадаче: «в работе» — до первой
  команды подзадачи; «выполнена» и итог — сразу после проверки её условия, до начала
  следующей.
- При статусе «выполнена» — раздел `## Итог` перед «Связями»: что сделано, какие
  файлы и заметки появились, чем проверено (команда и результат), 2–5 строк. Итог
  выводи и пользователю в сессии.
- Родительская задача выполнена, когда выполнены все её подзадачи; её итог — сводка
  по подзадачам.
- «Принята» ставится только после слов пользователя «принимаю» (или равных по
  смыслу) и распространяется на подзадачи. В итог допиши строку «Принято
  пользователем: «<его слова>»». Просьба переделать возвращает задачу в статус
  «в работе».

### 2.5. Данные и источники

Где что лежит — в `INDEX.md`. Прочитай его первым и открывай только нужные файлы по
ссылкам оттуда.

- `data/gec-0km-2025.csv` — исходный 15-минутный ряд GEC за 2025 год, 34 944 строки,
  разделитель — пробелы, столбцы `Year Month Day DOY Hour Minute UnixTimestamp uqrg`.
- `data/holes.csv` — площадь областей, похожих на CH, по моментам времени; запятая,
  столбцы `date,polariz,freq,area_holes`; 722 строки, время только 03:00:00 и
  07:00:00, `polariz` и `freq` постоянны (`I`, `3000`).
- `data/gec-0km-2025-hours.csv` — производный файл: те же столбцы и порядок строк,
  что у источника, только моменты из `data/holes.csv`; 720 строк, разделитель —
  пробел. Пишется `src/build_specific_gec.py`; читать с `sep=r"\s+"`.

#### Чего агент не может знать сам

- `area_holes` — безразмерное отношение площади областей, похожих на корональные
  дыры, к площади солнечного диска; значения в файле уже в этой шкале, не умножать
  на 100 и не переводить в Мм² без решения исследователя. Это автоматическая оценка
  «похожих на CH» областей, а не каталог CH.
- `uqrg` — глобальное электронное содержание (GEC) в TECU; это не концентрация
  электронов и не TEC каждого отдельного пункта наблюдения.
- В `data/gec-0km-2025.csv` отсутствует весь день 2025-11-26 (96 отсчётов). Поэтому
  в `data/gec-0km-2025-hours.csv` 720 строк, а не 722: нет 03:00 и 07:00 этого дня,
  хотя они есть в `data/holes.csv`. `checks/check.py` на этом красный — это ожидаемо.
  Не интерполировать, не подставлять соседние дни и не дополнять результат; решение
  принимает человек.
- `data/gec-0km-2025-hours.csv` — отфильтрованное подмножество исходного ряда
  (только 03:00 и 07:00 из `data/holes.csv`), а не независимая выборка. Сравнение
  средних по двум файлам показывает эффект отбора моментов, а не двух независимых
  рядов.
- `UnixTimestamp` и столбцы `Year…Minute` в GEC — UTC; `date` из `holes.csv`
  сопоставляется с ними по календарным полям без пересчёта часовых поясов.
- `memory/L2.md` и `L3.md` — сжатие статьи об апрельском событии 2010 г., а не
  результат по данным 2025 г. Числа и выводы статьи нельзя переносить в анализ
  GEC–CH за 2025 г.
- Источник и URL исходного GEC в проекте не зафиксированы. Не выдумывать источник и
  не создавать экземпляры `Скачивание`, пока человек не назовёт происхождение файла.
- `src/build_specific_gec.py` — фильтр GEC; `checks/check.py` — проверка результата
  (только чтение). Официального `check_week4.py` в проекте нет; не подменять его
  самодельным файлом с тем же именем.

## 3. Инструменты и границы

Python 3.12 и пакеты из `.venv` (pandas, matplotlib, PyYAML); новые зависимости не
устанавливать. Запуск только из корня проекта:

```
.venv/bin/python src/build_specific_gec.py
.venv/bin/python checks/check.py
.venv/bin/python src/plot_gec.py
.venv/bin/python src/calc_gec_average.py data/gec-0km-2025.csv
```

Сеть и Lean не нужны: `AI4SCIENCE_WEB_DISABLED=1 ai4science --no-lean`. Расчёты —
скриптами в `src/`; временных файлов вне проекта не создавай — каждое число в
заметках воспроизводится командой из проекта.

## 4. Запреты

1. Не изменять и не удалять `data/gec-0km-2025.csv`, `data/holes.csv`,
   `ontology.yaml`; не изменять `checks/`. `[среда]` — файлы переведены в режим
   только чтения.
2. Не удалять никакие `.csv`. `[окно]`
3. Не удалять заметки задач и не менять «Готово, когда» после начала работы: если
   условие недостижимо — статус «заблокирована». `[окно]`
4. Не ставить статус «принята» без слов пользователя. `[окно]`
5. Не читать табличные файлы целиком в контекст модели: только шапка,
   первые/последние строки и агрегаты, полученные скриптом. `[окно]`
6. Не обращаться к сети за документацией; не читать и не изменять исходники
   `ai4science`. `[окно]`

## 5. Протокол работы

1. Прочитать `ontology.yaml`, заметки `tasks/` (статусы), `STATUS.md` и `diary.md`.
2. Проверить хранилище и заметки классов (2.1, 2.2).
3. Если сообщение принимает результат или просит переделать — сменить статусы (2.4).
4. Если сообщение ставит новую работу — записать задачу и подзадачи до любых
   расчётов, показать план. Сообщение может и принять прежнюю работу, и поставить
   новую: тогда сначала шаг 3, затем шаг 4.
5. Подзадачи по очереди: «в работе» → работа и заметки объектов по ходу (2.3) →
   проверка условия «Готово, когда» → «выполнена» и итог. Объём работы задают
   «Готово, когда» и «Не входит»: лишнего не создавай.
6. Проверить граф: у каждого объекта есть `type` и строка `- тип: [[Класс]]`, концы
   связей согласованы с `ontology.yaml`, у выполненных задач есть «Итог», правила
   П1–П3 выполнены. Данные проверить командой `.venv/bin/python checks/check.py`
   (ожидаемо красный на 2025-11-26).
7. Дописать `diary.md`; ответить пользователю: итоги подзадач, что ждёт его решения.

## 6. Память

- В начале сессии прочитать `STATUS.md`. После каждого блока работы перезаписать его
  целиком: где работа, что дальше, какие ограничения действуют.
- `diary.md` только дописывается: дата, запрос, результат, команда проверки и её код.
  Старые записи не менять.
- Коммит — по указанию человека; в сообщении — что изменено и зачем.

## 7. Остановка и эскалация

- Бюджет эпизода: 50 шагов.
- При исчерпании бюджета — отчёт: что сделано, что нет, где остановились.
- Стоп и вопрос человеку: две неудачи проверки подряд по одной причине; в
  `holes.csv` есть момент, которого нет в GEC; формат данных не совпал с описанием;
  для объекта нет класса в онтологии; правило требует экземпляр, которого нельзя
  создать честно.
